# Change contract, L3 cycle 1: trade-lifecycle on duckdb-native

- **Prior policy authority:** `chain/l2/trade-lifecycle/semantic-model.json` restricted to `chain/l2/trade-lifecycle/review.json` `selected_element_ids` (verdict must be pass; use its model_sha256). Upstream entity `governed.account` exists from the ownership-history projection on this target; consume it only through the handoffs the model names.
- **Exact active change authority:** none. Initial compilation.
- **Stable projection contracts:** `chain/anchors/DEVELOPER-CONTRACT-L2-L3.md`; profile `chain/profiles/duckdb-native.json`. Output under `chain/l3/duckdb-native/trade-lifecycle/`: `manifest.json`, `trade.sql`, `audits/<invariant id>.sql` for every selected deterministic invariant.
- **Write surface:** `logical.trade` is incremental_by_identity. Per the profile, implement it as: create `governed.trade` if it does not exist with the model's attributes; then `MERGE INTO governed.trade` using a source query of the incoming reports, `ON` the identity (trade_number), `WHEN MATCHED THEN UPDATE SET` exactly the mutable-role attributes (status, executed_price, fees, commission, tax, quantity), `WHEN NOT MATCHED THEN INSERT` all attributes. The gate's write guard rejects any frozen attribute (owning_account_number, placed_at, owning_account_effective_from, owning_customer_number, first_seen_late) in the matched update.
- **Selectors:** `first_encounter_only` values come from the trade's earliest report by the anchored report_order (batch_date, cdc_dsn), evaluated only when the trade is not yet present; `latest_change` values come from the latest I or U report (D rows excluded, as the model states provisionally); `as_of_event_time` resolves the account statement whose effective_from is the latest at or before placed_at for owning_account_number; `same_statement_as_owning_account_reference` reads owning_customer_number from that statement; first_seen_late follows the model's rule over the anchored status_order.
- **Simulation:** `chain_l3.py run duckdb-native trade-lifecycle` loads the fixture in its rollover phase (Batch1 plus Batch2 rows and the labeled constructed account change) and executes ownership-history first. For the fixture, the expected behavior is that trade 372101's ownership reference pins account 428's statement effective at its 2017-04-10 placement (the 2012 closed statement), not the 2017-07-08 constructed statement, and that its outcome shows the completed report's values.
- **Forbidden shortcuts / conflict protocol:** unchanged. If the model does not say how the MERGE source should treat several reports of one trade within a single run, file the question rather than choose.
